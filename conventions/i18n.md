# i18n Conventions for spine-toolkit

> Adapted from spine-toolkit's convention. Plugins share no code; update both or neither.
> Adapted from spine-toolkit conventions/i18n.md sha256:42d0efa6da7f061a230a819cd7bc9d16a2d3d65a442ca1fca660bc6c1c4c8a19
> The CLAUDE.md stub is named by owner, not by path: a bare relative path here would resolve
> under this plugin's root, where the file does not exist.

## Goal

spine-toolkit and its platform plugins are single-source-of-truth in English. User-facing strings are localized per user's chosen language. Currently supported: `en`, `ru`.

## Where strings live

| String type                                  | File                                                     | Language |
|----------------------------------------------|----------------------------------------------------------|----------|
| Skill body (algorithm, structure, contracts) | `skills/<name>/SKILL.md`                                 | EN only  |
| Skill user-facing strings                    | `skills/<name>/locales/<lang>.md`                        | per lang |
| Agent body (platform plugins; core ships none) | `<plugin>/agents/<name>.md`                            | EN only  |
| Agent description (frontmatter)              | `<plugin>/agents/<name>.md` frontmatter                  | bilingual |
| Command description (frontmatter)            | `commands/<name>.md` frontmatter                         | bilingual one-line |
| Command body                                 | `commands/<name>.md` body                                | EN only  |
| CLAUDE.md stub (copied to user projects)     | spine-toolkit-owned — one file per lang                  | per lang |
| Artifact **structure** (headings, field labels, status enums) | `Task.md` / `Research.md` / `Plan.md` / `Validation.md` / `Review.md` / `Done.md` / `OpsChecklist.md` etc. in the user's project | **EN only** (stable, parseable) |
| Artifact **prose** (free-form body the toolkit/agent composes under those headings) | same files | **per project `## Language`** |
| README                                       | `README.md` (EN); `docs/readme.ru.md` (optional mirror)  | EN main, RU mirror |

## What is user-facing

(Same definitions as in the plan's Conventions section. Reproduced here so this spec is self-contained.)

A string is **user-facing** (localized) if any of these hold:
1. Printed to chat as Claude's reply.
2. Used as structured question text/header/option label.

A string is **internal** (always EN) if any of these hold:
- It's a stable identifier (`name:` field, contract field, status enum value).
- It's a stack axis name or one of the values the platform manifest's `## Axes` lists for it
  (`ui`, `Compose`, `manual`) — rendered as AUQ option labels, but matched back against that
  catalog, so a translated option resolves nothing.
- It's a file path, glob, command name, env var.
- It documents algorithm steps inside the skill body.
- **It's a section heading or structural label written into a Markdown file by the toolkit** (`Task.md`, `Done.md`, `Plan.md`, `Research.md`, `ChangesRequested.md`, `Review.md`, etc.). File templates are stable EN structure so downstream skills can parse them and so files don't break when `LANG` is switched mid-project.

Free-form **content** the user composes inside an artifact (prose under a heading, notes under bullet points) follows the user's language naturally — not a localized template, just user input.

### Artifact authoring rule (agents + skills that write project files)

This is the single most violated rule, so it is stated explicitly here and
referenced from every agent body and artifact-producing skill:

> When the toolkit or a subagent **writes or fills** an artifact in the user's
> project (`Task.md`, `Research.md`, `Plan.md`, `Validation.md`, `Review.md`,
> `Done.md`, `OpsChecklist.md`, …) **and the agent's final report back to the
> orchestrator**:
> - **Structure stays EN**: section headings (`## 2. [Description]`,
>   `## Validation`, `## What was refactored`), field labels and status enums
>   (`[TASK_TYPE]`, `[STATUS] = [DONE]`, `[VALIDATION_STATUS] = PASSED`),
>   table header cells the toolkit parses. Never translate these — downstream
>   skills key off them and they must survive a mid-project `LANG` switch.
> - **Prose is written in the project `## Language`**: every sentence the
>   agent composes under those headings, bullet notes, rationale, the final
>   summary message. If `## Language` is `ru`, the body is Russian even though
>   the headings are English.
> - **Always EN regardless of language**: code, identifiers, file paths,
>   commit subject/body, shell commands, log/stack-trace excerpts quoted
>   verbatim.

Concrete example (`## Language` = `ru`):

```markdown
## What was refactored        <- EN heading (structural, parseable)

`FooDataProvider` переведён на диффабл-источник: выделение теперь
рендерится из модели, а не из тапа.   <- RU prose (project language)
```

Mixing modes (English prose under English headings, or translated headings) is
a defect — the first breaks the language contract, the second breaks parsing.

## Locale file format

`skills/<name>/locales/en.md` and `ru.md`. Both MUST have identical key sets.

Example (`skills/<name>/locales/en.md`):

```markdown
# <name> — en

## error_no_task_id
Specify task number, e.g. `/spine-toolkit:task-run 026`.

## confirm_dispatch
Profile: {profile}, mode: {mode}, stack: {stack}, start: {start_stage}. Correct?
```

Keys are `lower_snake_case`. Placeholders use `{name}`.

## Language resolution

Every localized skill carries a `## Language Resolution` section, and it names the config that
skill actually reads. A skill that runs inside a project root uses the steps below verbatim; a
skill that resolves a different config — a workspace meta-repo's, say — states its own lookup
instead. The section is not optional and may not point at a config the skill does not read.

1. Read `CLAUDE-spine-toolkit.md` from project root.
2. Find `## Language` section.
3. First non-empty line, lowercased and trimmed = `<lang>`.
4. If `<lang>` ∈ {`en`, `ru`} → use it. Otherwise default to `en`.
5. Read `locales/<lang>.md` of the calling skill. Look up by H2.
6. Missing key → fallback to `en`. Still missing → bug, fail loudly.

Cache `<lang>` once per skill invocation.

## Bilingual triggers

Skill / agent description:

```yaml
description: |
  <EN summary>.
  Use when (en): "<trigger 1>", "<trigger 2>"
  Use when (ru): "<триггер 1>", "<триггер 2>"
```

Command description (one-line):

```yaml
description: "<EN summary> / <RU summary>"
```

## How to add a new language

1. For each localized skill, copy `locales/en.md` to `locales/<new>.md` and translate values (keep keys).
2. Add `<new>` to the supported list in this plugin's own locales, and ask spine-toolkit to add it to `setup`'s language question and the resolution allowlist.
3. The CLAUDE.md stub is spine-toolkit-owned; the new language needs a copy there too.
4. Optionally extend `description:` triggers to include `Use when (<new>):` lines for the most common patterns.

## Orphaned keys

A key defined in `locales/` but named nowhere in its own skill's body is a string nothing can ever
emit — or a string the body emits by inlining, which the "reference the key, never the text" rule
forbids. Either way it is a defect. Two forms of reference count besides the literal name:

- a **placeholder template** — a body writing `` `auq_axis_<axis>_question` `` references every key
  matching `auq_axis_*_question`;
- a **glob family** — a body writing `` `preflight_*` `` references the whole family.

Both are legitimate and load-bearing; a check that does not honour them reports ten false positives
in this repo alone. Scanning every skill with those two rules applied (and exempting `description`, which nothing
references by design) leaves 0 orphans in this plugin: `kotlin-setup` is the only localized skill
and every key it declares is named in its body.

This is **not yet enforced**. Shipping the check today would need an allowlist of exactly these
entries, and none of them is a legitimate dynamic reference — an allowlist would be a list of frozen
defects. The order to fix it in: name the missing keys in the bodies that should have named them
(most are a one-line edit adding a key or a `<role>` template), decide the genuinely ambiguous ones
(reference or delete from every locale), then ship the check with the two pattern rules and **no
allowlist**, wired into the required lint sweep. A lint that starts at zero stays at zero; one that
ships with its violations exempted never gets back to zero.

## The `## Language` anchor

Language resolution reads one block of the project config, so that block's position and name are
part of the i18n contract: `## Language` is the first H2 in the file — after the H1 title and any
blockquote intro — and the heading itself is English and never translated, because it is the anchor
the procedure above keys on. The rest of the config's schema lives in the template
`spine-toolkit:setup` renders it from.
